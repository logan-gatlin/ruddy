# Rust source backend feasibility

Investigated 2026-09-05 against checkout `c5b7e0a`. This is a feasibility note, not an accepted design or implementation spec. Scope assumption: compile Ruddy to Rust source that `rustc`/Cargo builds; implementing a backend inside `rustc` is a different project. No implementation or tests were run.

## Recommendation

**Feasible: start with generated Rust functions plus a small dynamic runtime consuming linked artifacts.** Existing lowering has already done closure conversion, currying adaptation, pattern compilation, and effect-evidence plumbing. The difficult work is runtime representation, foreign bindings, and defining cross-target semantics—not translating the parser or inference engine. This conclusion is an inference from the concrete LIR operations and existing JavaScript backend, not a demonstrated prototype. [LIR](../../src/lir.rs), [JavaScript generator](../../src/backend/js.rs)

Do not make a fully specialized, idiomatic Rust API a prerequisite. LIR deliberately erases structural type information and represents quantified types as `Rep::Any`; its function records carry parameters and bodies without an explicit return representation. A uniform `Value` ABI fits that information today. Generating concrete Rust record types, generic function signatures, and specialized closures would require extra layout/signature analysis or a richer IR. Public artifact headers retain schemes, but that does not reconstruct every internal temporary's erased shape. [Representation definition](../../src/lir.rs), [artifact function and header definitions](../../src/artifact.rs)

| Approach | Feasibility in current architecture | Recommendation |
| --- | --- | --- |
| Rust source with tagged values and generated functions | Maps existing linked LIR directly; runtime and extern port remain substantial | First prototype |
| Hybrid native scalar locals plus dynamic aggregates/closures | Possible using `Rep`, with explicit boxing at calls and joins | Profile after correctness |
| Fully specialized Rust structs/enums/generics | Missing internal layouts, indirect signatures and monomorphization | Separate compiler project |

These are engineering assessments, not performance predictions. Rust compilation alone does not remove dynamic dispatch, reference counting, record lookup, or array copying.

## What the compiler already supplies

Observed in [LIR](../../src/lir.rs): functions are lifted, captures are explicit, direct/indirect calls are distinguished, and every temporary is assigned once. Structured child blocks terminate with `Yield`; function/global blocks terminate with `Ret`; `Throw` carries a dynamic handler tag and value. Records support merge, projection and runtime presence/rest tests; arrays support concatenation and pattern slices; sums have explicit tags and payloads. The hidden unnamed operation uses a distinct `FieldKey` variant, so it must not collapse into a user-spellable field name.

Observed in [artifact definitions](../../src/artifact.rs) and [JavaScript generator](../../src/backend/js.rs): the backend seam is the validated, **linked `Artifact`**, not the inference AST or source LIR. JavaScript generation is deterministic and performs no I/O. A Rust backend should follow that contract, validate references/exports and produce source before the driver installs output. This keeps compiler passes and library artifacts shared and follows the existing requirement that backend generation and target-syntax validation stay outside core compilation. [Compiler architecture spec](../compiler-architecture-deepening/spec.md)

## Proposed runtime and lowering strategy

This section proposes a design; it is not existing code.

Use a closed runtime enum covering natural/integer/real, boolean, unit, string, record, array, sum, closure, host callable and handler identity. Store recursive aggregate payloads and capture arrays behind shared ownership. Start with all generated parameters/results as `Value`, cloning cheap handles where an SSA temporary has multiple uses. Rust requires indirection to make recursive layouts finite; a nominal enum with `Rc`/`Box` supplies it. [`Rust Reference: recursive types`](https://doc.rust-lang.org/reference/types.html#recursive-types)

For closures, reuse `Op::Closure { func, captures }` literally: a generated function identity or function pointer plus `Rc<[Value]>` captures. A shared invocation entry accepts a runtime context and arguments, then calls generated Rust functions. Direct LIR calls can name generated functions directly. Each native Rust closure expression has a distinct anonymous type, so generating arbitrary `impl Fn` values would not itself give the uniform heterogeneous representation needed for `Rep::Fn` and `Rep::Any`. A trait object behind `Rc` is an alternative for host callbacks, but is unnecessary for already lifted Ruddy functions. [LIR closures](../../src/lir.rs), [Rust closure types](https://doc.rust-lang.org/reference/types/closure.html), [Rust trait objects](https://doc.rust-lang.org/reference/types/trait-object.html)

Keep globals in a per-program runtime context initialized in artifact order. Closures should contain function identity and lexical captures rather than owning their entire global context; pass the context when invoking them. Read/clone a global out of its slot before calling user code so a borrow does not remain active across reentrant execution. Do not initialize globals lazily unless equivalence of initialization effects has been established. Existing lowering reconstructs a local recursive function from its identity and captures rather than capturing its not-yet-created self. That avoids needing a self-owning closure merely for recursion. [Global order and `Recursive`](../../src/lir.rs), [linked global construction](../../src/link.rs)

Single-threaded `Rc` is a reasonable prototype assumption, not a threading guarantee. Reference-count cycles leak, and `Rc` cannot cross threads; audit host closures and mutable host state for cycles before deciding it is sufficient for a production embedding API. Deep recursion and recursive destruction also need stress measurements; this design does not promise bounded stack use. [Rust `Rc`](https://doc.rust-lang.org/std/rc/index.html)

Map record fields to runtime keys, with a reserved enum key for the unnamed operation. Preserve later-field-wins merge behavior and absence separately from unit. Map sums to name/ID plus optional payload. Immutable `Rc<Vec<Value>>` arrays with copied slices/concatenations can establish semantic feasibility, but do not claim equivalent cost to the existing persistent RRB implementation. Production array choice needs the standard library operations and workload measurements, not just LIR literal support. [LIR operations](../../src/lir.rs), [current array runtime](../../src/backend/js.rs), [array conformance fixture](../../tests/bundles/arrays/arrays.test.mjs)

### Effects require propagation, not captured continuations

Observed: an operation arm returns the value with which its call site resumes. The handler return arm is lowered inside the handled child block; a matching `Throw` becomes the `Catch` instruction's value and bypasses that return arm. Nested handlers distinguish dynamic identities even for the same effect. There is no first-class continuation/resume operation in this LIR. Thus a continuation-passing transformation is not required for the current effect model. [Handler lowering and `arm`](../../src/lir.rs), [JavaScript `$catch`](../../src/backend/js.rs)

Proposed function/block result:

```rust
type Eval = Result<Value, Raised>;
struct Raised { tag: HandlerId, value: Value }
```

Emit normal return/yield as `Ok(value)` and `Throw` as `Err(Raised { .. })`. Propagate calls with `?`; evaluate each catch body in its own generated helper or Rust closure returning `Eval`, then match its result: unwrap a matching tag and propagate a nonmatching one. The separate result boundary matters: `?` inside a plain lexical block would otherwise escape the enclosing function before its intended handler sees it. Every possibly propagating child expression, including switch branches and initializers, must follow the same rule. Generate fresh opaque identities, for example `Rc` allocation identity, and preserve them through captures. [Rust error propagation](https://doc.rust-lang.org/reference/expressions/operator-expr.html#the-question-mark-operator)

Do not implement ordinary Ruddy `raise` with Rust panic unwinding. Rust documents `catch_unwind` as unsuitable for routine try/catch use; it catches unwinding panics, not aborting panics. Explicit results also keep host/runtime faults distinct from a handled Ruddy effect. [Rust `catch_unwind`](https://doc.rust-lang.org/std/panic/fn.catch_unwind.html)

## Main integration blockers

1. **Foreign bindings are currently JavaScript-specific.** Artifact externs contain one target source string, and `std` embeds `Math.*`, `Object.is`, JavaScript lambdas and `$array*` runtime helpers. The linker copies all externs from its input artifacts; an unused binding is not automatically removed. A supposedly pure program linked with today's `std` can therefore still contain incompatible extern targets. The first spike should use a dependency-free fixture and reject unsupported externs clearly. [Extern representation](../../src/artifact.rs), [linker](../../src/link.rs), [standard library](../../std)
2. **Choose a binding contract before porting `std`.** Prefer target-indexed bindings or a target-neutral intrinsic/host-binding registry with explicit backend resolution. Merely accepting Rust text in today's undifferentiated string makes cross-target library artifacts ambiguous. Preserve `RawCall`'s visible-argument-only boundary; lowering already emits adapters to consume Ruddy evidence. Introduce checked host-call arity/value conversion and define how Rust host callbacks participate in `Eval`. Public Rust wrappers can be generated later from exported schemes where representable. [Extern adapters](../../src/externs.rs), [LIR `RawCall`](../../src/lir.rs)
3. **Driver/build packaging needs a Rust route.** Targets currently include library and JavaScript, and run configuration is JavaScript/Node-oriented. Add a Rust source target and clear generated-crate location before adding automatic Cargo compilation/run. Keep toolchain diagnostics and generated-code failures separate from Ruddy diagnostics; stage output and preserve the existing build on failure. Use stable Rust initially, with an explicit supported toolchain and runtime version policy. [CLI target/config/build/run](../../cli/src/lib.rs)

For the first fixture, `[dependencies] std = false` disables implicit standard-library injection. The debugger also currently generates JavaScript; a completed backend needs a Rust source/diagnostics view under the repository's debugger-support convention. If native compiled outputs are cached, their cache keys must include the Rust toolchain, target, runtime, dependencies and build profile; this is separate from the existing compiler artifact cache. [CLI configuration and caches](../../cli/src/lib.rs), [debugger snapshot](../../debug/src/snapshot.rs), [contributor instructions](../../CONTRIBUTING.md)

## Cross-target semantics must be decided explicitly

Observed: `Rep::Nat` and `Rep::Int` are documented as 64-bit integers, while emitted JavaScript uses ordinary numeric literals/operators and integer division truncation; natural subtraction clamps at zero. Standard library bindings also use JavaScript numeric functions. Mapping these mechanically to Rust `u64`/`i64` changes boundary behavior. Specify overflow, division by zero, conversions and values beyond exact JavaScript integer precision before claiming parity. A first numeric prototype may restrict its accepted range, but must report that restriction. [Representations](../../src/lir.rs), [arithmetic generation](../../src/backend/js.rs), [integer stdlib](../../std/int.rud), [natural stdlib](../../std/nat.rud)

Observed: string bindings use JavaScript length/index/slice/reverse operations; real equality uses `Object.is`, and rounding uses `Math.round`. Rust `str` is UTF-8 and `len()` counts bytes, so Rust strings cannot be substituted without checking the intended indexing model. If exact JavaScript string behavior is required, use an explicit code-unit representation able to preserve isolated surrogate results rather than assuming `String` can hold every result. Alternatively define language-level Unicode behavior and align both backends. Test NaN, signed zero and rounding ties independently. Preserve real literal bits with `f64::from_bits`, mirroring the JS bit decoder, while treating arithmetic NaN behavior separately. [String stdlib](../../std/str.rud), [real stdlib](../../std/real.rud), [Rust `str`](https://doc.rust-lang.org/std/primitive.str.html), [Rust `f64::from_bits`](https://doc.rust-lang.org/std/primitive.f64.html#method.from_bits)

## Staged experiment and acceptance gates

1. **Source generation spike:** dependency-free linked artifact to one self-contained Rust source/module using `Value`. Compile and execute constants, polymorphic identity at two representations, records/open merges, sums, arrays and pattern branches. Require deterministic source and results matching the current backend on the explicitly agreed semantic subset. Include hostile field names and unusual literals.
2. **Closures and effects gate:** escaping captures, multiple invocations, currying/partial application, direct/indirect calls, local and top-level recursion, operation-value adapters, normal handler return, matching raise, nonmatching raise through an inner handler, and recursively nested same-effect handlers. Include raise propagation through switch/catch child blocks and initialization. These cases must pass before committing to the ABI. Reuse Ruddy fixture sources and write Rust assertions rather than treating existing JavaScript assertions as portable. [JS tests](../../tests/src/js.rs), [LIR tests](../../tests/src/lir.rs), [runtime fixture runner](../../tests/src/runtime.rs)
3. **Usable backend gate:** target-specific extern resolution, a minimal `std` slice, one Rust host callback, one exported callable, CLI generated crate/build/run, missing-toolchain diagnostics and failure-safe output replacement. Document unsupported APIs instead of accidentally compiling JS bindings.
4. **Performance gate:** measure Rust build time, emitted source size, executable size, execution time, allocations/peak memory and stack behavior on arithmetic, recursive functions, closure-heavy effects, record merges and array workloads. Compare release configurations and separate compiler time from program runtime. Only then consider unboxing, call specialization, a persistent array implementation, tail-call transformation or richer typed lowering.

Future repository Rust tests must run through `just test` only, per [AGENTS.md](../../AGENTS.md). This investigation adds documentation only; no prototype has yet demonstrated these acceptance gates.
